# Changelog

## 1.0.9

- **Найдена настоящая причина HTTP 401 от камер: пароль камеры зашифрован.**
  Сервер отдаёт в `/mobile1/barrier/addresses` поле `Password` камеры в
  виде `base64(шифротекст);base64(IV)`, и приложение перед Basic-авторизацией
  **расшифровывает** его (`Snapshot.CheckPassword` → `SecureStringExtensions.
  Decrypt` в EgdsMaui.dll): AES-256-CBC + PKCS7, ключ — PBKDF2-HMAC-SHA1
  (`"OurSecretKey#1"`, фиксированная соль, 300 итераций, 32 байта).
  Интеграция отправляла на камеру зашифрованную строку как есть — камера
  отвечала 401, хотя соединение и TLS были в порядке. Теперь пароль
  расшифровывается при разборе ответа сервера; если строка не в ожидаемом
  формате — используется как есть (совместимость с открытым паролем).
  Алгоритм восстановлен по IL-коду приложения и проверен сквозным
  мок-тестом: сервер в тесте шифрует пароль, клиент — расшифровывает и
  проходит авторизацию камеры.
- Диагностика 401 из v1.0.8 (перечитывание учётных данных, атрибут
  `credentials_present`) сохранена — она полезна, если пароль камеры
  действительно сменён на сервере.

## 1.0.8

- **Исправлен HTTP 401 от камер («Поток камеры: HTTP 401» в журнале).**
  Сервер ЕГДС ротонирует учётные данные камер (Login/Password из ответа
  `/mobile1/barrier/addresses`) — это видно и по приложению, где загрузчик
  видео периодически пересинхронизирует их. Интеграция же кэшировала
  камеру один раз при старте HA, и после смены пароля камера отвечала
  401, хотя в приложении видео работало. Теперь:
  - сущность камеры перед каждым снимком/потоком берёт свежую карточку
    камеры (host/port/guid/login/password) из последнего опроса координатора;
  - при 401/403 клиент автоматически перечитывает адреса у сервера
    и повторяет запрос с новыми учётными данными (один раз, под замком,
    чтобы несколько камер не устроили бурю перечитываний);
  - об успешной смене учётных данных пишется INFO-запись.
- **В атрибуты камеры добавлен `credentials_present`** (`true`/`false`)
  — пришёл ли от сервера набор учётных данных камеры, без раскрытия самих
  значений. Если камера стабильно отвечает 401 и атрибут `false` —
  сервер не прислал Login/Password для этой камеры.
- Мок-тест дополнен сценариями: ротация пароля между запросами (snapshot
  и mjpeg ретраят успешно), устойчивый 401, пустые учётные данные.

## 1.0.7

- **В атрибуты камеры добавлены `camera_port` и `camera_url`** — полный
  адрес снимка, который использует интеграция. Теперь можно открыть URL
  в браузере на машине с Home Assistant и сразу увидеть, доступна ли
  камера из сети HA (без учётных данных в URL — авторизация передаётся
  в заголовке отдельно).

## 1.0.6

- **Главный кандидат на причину «пустого окна камеры» закрыт: TLS-сертификаты
  камер.** Хост камеры ЕГДС почти всегда IP-адрес с самоподписанным
  сертификатом — проверка TLS рвала соединение ещё до запроса кадра. Теперь
  запросы к камерам по умолчанию не проверяют сертификат (как в приложении);
  параметр «Проверять TLS-сертификаты камер» в параметрах интеграции
  возвращает строгую проверку при желании. На запросы к API-серверу ЕГДС
  опция не влияет.
- **Пустое окно камеры теперь объясняется в журнале.** Неудача снимка или
  потока (HTTP-статус, SSL-ошибка, таймаут, отказ соединения) пишется в
  журнал HA как WARNING — не чаще одного раза в 5 минут на каждую причину,
  с URL камеры и классом ошибки.
- Локальный e2e-тест API (snapshot + mjpeg через мок-сервер) прогнан
  после изменений.

## 1.0.4

- **Профилактика ошибки `already_in_progress` при добавлении интеграции**
  (та же правка, что и в А.М.Видео 1.0.4). Незавершённая попытка
  настройки (закрыли окно с кодом, код не пришёл, рестарт HA посреди
  настройки) оставалась «в работе» и пережила бы любой рестарт Home
  Assistant — а каждая новая попытка добавления обрывалась сообщением
  `already_in_progress`. Теперь при старте настройки интеграция сама
  прерывает зависшие попытки того же аккаунта.
- Если аккаунт успели настроить из другого окна, пока ждали код, —
  вторая запись не создаётся (мастер закроется с «Этот аккаунт уже
  настроен»).
- Добавлен человекочитаемый перевод abort-причины `already_in_progress`.

## 1.0.3

- **Токены больше не теряются при обновлении.** Сервер ЕГДС ротонирует
  `refresh_token` при каждом обновлении — свежий токен сохранялся только
  в памяти и пропадал при рестарте Home Assistant, после чего требовался
  повторный вход по SMS (а свежий login завершал сессию приложения на
  телефоне). Теперь обновлённые токены сразу сохраняются в запись
  конфигурации (без перезагрузки интеграции).
- **Проактивное обновление** `access_token` за 2 минуты до истечения
  (`token_expires`), а не по факту 401 — меньше отказов и разрывов опроса.
- **Повторная авторизация из настроек.** В настройках интеграции
  (Настройки → ЕГДС → ⚙) появилось меню: «Параметры опроса, таймингов и
  видео» и «**Повторная авторизация (новый код)**» — запускает reauth
  вручную в любой момент, удалять и добавлять интеграцию не нужно.
- Reauth теперь **сразу высылает новый код** при старте — остаётся только
  ввести его (галочка «Выслать код повторно» осталась на случай сбоя).
- Подсказки доставки кода уточнены по приложению 3.3.25: SMS и звонок
  (код — последние 4 цифры номера звонившего) доступны всем при входе;
  Telegram (t.me/egdsk_bot) и email подключаются в приложении —
  «Настройки уведомлений» → «Запросить подтверждение EMail» / «подтвердите
  телефон в чат-боте». Личный кабинет на сайте для этого не нужен.

## 1.0.2

  лицам по договору): в приложении ЕГДС «Настройки уведомлений» (подтвердить

  мини-приложении lk.egdsk.ru (мессенджер MAX).
- Ответ «Сбой в работе сервера» интерпретируется как временная проблема
  на стороне ЕГДС и сопровождается советом повторить позже.
- Подсказка на шаге входа перечисляет все способы доставки кода, включая
  вариант приложения «звонок» (код — последние 4 цифры номера звонившего).
- Проверено живыми запросами: формат телефона и эндпоинт верны
  (String.Concat("7", 10 цифр) из IL-кода приложения), password-грант
  работает, отказ происходит на шлюзе доставки кодов.
